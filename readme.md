# Mystery Delivery System

A Python-based logistics simulation for a fictional delivery company called **FastBox**.

The project simulates one day of delivery operations using warehouses, delivery agents, and packages. It assigns each package to the nearest agent, calculates delivery distances, tracks agent performance, and generates a final JSON report.

## Features

### Core Features

- Read and parse delivery data from a JSON file
- Calculate Euclidean distance between coordinates
- Assign each package to the nearest delivery agent
- Simulate package pickup and delivery
- Track each agent's current location
- Calculate total distance travelled by each agent
- Calculate delivery efficiency
- Identify the best-performing agent
- Generate `report.json`

### Bonus Features

- Random delivery delays
- ASCII route visualization
- New agent joining during the day
- Export top performer to CSV

## Distance Calculation

The project uses Euclidean distance:

```text
distance = √((x2 - x1)² + (y2 - y1)²)
```

For example, for:

```text
Point 1 = [5, 5]
Point 2 = [0, 0]
```

the distance is:

```text
√((5 - 0)² + (5 - 0)²)
= √50
≈ 7.07
```

This distance is used to determine the nearest agent to a warehouse.

## Package Assignment

For each package:

1. Read the warehouse assigned to the package.
2. Get the warehouse coordinates.
3. Calculate the distance from every agent to that warehouse.
4. Select the agent with the smallest distance.
5. Store the package under that agent.

Example:

```text
A1 → P1, P4
A2 → P2, P5
A3 → P3
```

## Delivery Simulation

For every assigned package, the route is:

```text
Agent Current Location
        ↓
Warehouse
        ↓
Package Destination
```

The total distance for a package is:

```text
Agent → Warehouse
+
Warehouse → Destination
```

After the delivery is completed, the agent's current location is updated to the package destination.

This means the next delivery starts from the agent's new location instead of the original starting position.

## Agent Statistics

For every agent, the program tracks:

```json
{
    "packages_delivered": 2,
    "total_distance": 100.50,
    "efficiency": 50.25
}
```

Efficiency is calculated as:

```text
efficiency = total_distance / packages_delivered
```

Agents that delivered zero packages are not considered when selecting the best agent.

## Best Agent

The best agent is selected using the lowest efficiency value among agents that delivered at least one package.

The final report contains:

```json
{
    "A1": {
        "packages_delivered": 2,
        "total_distance": 85.32,
        "efficiency": 42.66
    },
    "A2": {
        "packages_delivered": 2,
        "total_distance": 120.12,

    },
    "A3": {
        "packages_delivered": 1,
        "total_distance": 50.00,
        "efficiency": 50.00
    },
    "best_agent": "A1"
}
```

## Logic Assumptions

The following assumptions were made because the assignment allows interpretation:

1. Each package is assigned to the nearest agent based on Euclidean distance from the agent to the package warehouse.
2. If two agents have the same distance, the agent encountered first in the input data is selected.
3. Packages are processed in the order they appear in the assignment/input.
4. After a package is delivered, the agent's current location becomes that package's destination.
5. Efficiency is calculated as total distance divided by packages delivered.
6. Agents with zero deliveries are not considered when selecting the best agent.
7. Random delivery delays are only used for simulation and do not affect travel distance.

## Technical Challenge

One of the main technical challenges was handling different JSON structures between the base case and some provided test cases.

For example, the base case uses lists of objects:

```json
"agents": [
    {"id": "A1", "location": [5, 5]}
]
```

while another test case uses a dictionary:

```json
"agents": {
    "A1": [89, 16]
}
```

The package warehouse key can also differ between inputs, such as:

```json
"warehouse_id": "W1"
```

or:

```json
"warehouse": "W1"
```

The code was adjusted to handle the structure of each provided input format.

Another issue was accidentally counting the same package multiple times due to nested loops. This was resolved by keeping the delivery/statistics logic inside the package-matching condition and using `break` after the matching package was processed.
